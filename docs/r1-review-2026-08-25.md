## 04 · Findings

### F1 — an unavailable reading counted as a system that disagrees · **fixed**

`fromAgentIssue` filtered `ignored` and `not-applicable` out of the evidence
ledger but left `unavailable` in. `EvidenceEntry.supports` is a boolean, so an
unavailable source landed as `supports: false` — indistinguishable from a system
saying *the problem is not there*. `confidenceFrom` returns `unclear` on any
dissent, so **one provider outage silently downgraded a corroborated diagnosis
to Unclear**, and the ledger showed a reading that had never been taken.

Three statements in the codebase already said this was wrong:

- `agentIssueCases.ts` header, rule 2: "Ignored, not-applicable, unavailable,
  partial, and failed are five distinct outcomes and never collapse into one
  another." Its own `caseStatus` and `caseConfidence` keep `unavailable` out of
  the determined set. The adapter downstream did not.
- Registry `checkpoint.unavailable`: "Neither agreement nor disagreement. Same
  condition as `agent_result.unavailable` on a different object."
- Registry rule 18: an absent measurement is not a small measurement.

**Fix:** `unavailable` joins the unreadable set. **Tests:** two, asserting
against the registry's sentences rather than the assembler's code. Verified by
reverting the fix — both fail; restored — both pass.

### F2 — `resolve` states a requirement nothing enforced · **fixed**

The registry says `action.resolve.requires: "checkpoint_agreement"`, and
`ISSUE_TRANSITIONS.resolve.requires` carried the word. `applyAction` only ever
enforced `requiresReason`. A case could reach **Resolved with three checkpoints
still scheduled** — the state whose whole meaning is "the evidence agreed and
held".

Nothing calls it today, so this never shipped a wrong Resolved. It is a
contradiction between two statements in the code, not a live incident.

**Fix:** the guard is enforced from the table (`transition.requires`), not from
a branch on the action's name, so a requirement added to `vocabulary.json`
cannot be carried in the type and ignored in the guard again. `checkpointsAgree`
is the registry's evaluation rules 1, 3, 4 and 5, and the interval that can fire
it is read off `CHECKPOINT_DAYS` rather than written as `"30d"`.

Two existing tests — "throws on every transition the registry does not name" and
"lands on the state the registry names" — were **asserting a legal move without
its stated requirement**. They now build the case from `action.requires`, the
same way they already built the reason from it. A requirement added to the
registry arrives there as a missing arm rather than a silently-satisfied one.

**Tests:** seven, one per registry evaluation sentence. Verified by mutation.

**Note for the owning chunk:** the checkpoint *scheduler* is still unbuilt.
`mark_fixed` schedules three checkpoints, nothing ever evaluates them, so
`resolve` remains unreachable in practice and `Watch` never drains. That is a
feature, not a review fix — **handed to W1**, the checkpoint chunk (evaluator,
the resolve transition, the three marks, the drawer). `checkpointsAgree` is the
predicate W1's evaluator should call rather than reimplement.

### F3 — the Watcher claimed stability over a device nobody measured · **fixed**

**This was reported as latent in the first pass. That was wrong — it is live.**

`watcher.ts` built its Accessibility/SEO stability claim like this:

```
(pageRangeComparison(p, strategy, key, rangeDays)?.delta ?? 0) <= -regression
&& (pageRangeComparison(p, strategy, key, rangeDays)?.to ?? 100) < regressionFloor
```

`rangeComparison` returns `null` when a page has fewer than two nights in range
for that device. `?? 100` then **fabricates a perfect score for a page that was
never measured** and `?? 0` fabricates a flat line, so the page counts as one
that held, and the Watcher prints:

> "Accessibility and SEO are stable across the board."

The first pass concluded this was unreachable, on the grounds that all four
categories share one `Night` and a page with no comparison is `pending`. Both
halves are true and the conclusion still does not follow, because the comparison
is taken **per device**:

- `availableStrategies` lets a night report desktop and not mobile.
- Under `devicePolicy: "both"`, `devicesForPolicy` returns `[]` for a single
  pending device, so one pending device no longer makes the page pending.
- The page is therefore ranked, and the stability check asks for its **mobile**
  comparison, which is `null`.

Reproduced directly: three desktop-only nights, `devicePolicy: "both"`, mobile
as the selected device — `winning` comes back
`"Accessibility and SEO are stable across the board."` over a device with no
readings at all. Supported settings, ordinary data.

The first pass tested only the both-devices-missing case and missed the
per-strategy asymmetry. The error was concluding "unreachable" from two probes
rather than from the code paths.

**Fix, in two parts, because the two ways of getting `null` are not the same
kind of event:**

1. **A missing reading is data, so the claim is withheld.** A page the selected
   device never measured neither held nor dropped, so it cannot be evidence for
   "across the board" — one unmeasured page withholds the claim for the whole
   board. Bad news still travels: a real drop is still reported.
2. **A malformed night is a broken invariant, so it fails loudly.** A `Night`
   carries all four categories for every strategy it reports; one that does not
   used to surface a `TypeError` from inside `median` naming a property rather
   than the invariant. `rangeComparison` now throws with the night, the strategy
   and the category in the message.

> **On the ruling.** It asked for the `null` path itself to throw, on the shared
> understanding that only a broken `NightScores` could produce it. A supported
> configuration produces it on ordinary data, so a throw there would have traded
> a false claim for a crashed dashboard on any workspace running
> `devicePolicy: "both"` with one device missing. The loud failure went to the
> invariant break — the case the ruling was actually about — and the data case
> withholds the claim. **Confirmed on review: this split is what ships, and the
> harder line on the data case was declined.**
>
> The distinction is now **registry rule 18** rather than a note in this file,
> so the next reader inherits it instead of re-deriving it.

**Tests:** four on the withholding (including that a real drop still reports),
one on the throw — the cast-constructed partial `NightScores` the ruling named.
Both halves verified by mutation.

### F4 — `confirmedRuns: options.confirmedRuns ?? 0` · **handed to S2**

`fromRec` sets `confirmedRuns` to 0 for every migrated case, because the legacy
record carries no count. The registry says `new` means "Detected **and
corroborated**". So a migrated case claims corroboration while recording zero
corroborating runs — rule 18's `?? 0`-on-an-unmeasured-value shape.

Harmless today: `confirmedRuns` is written in three places and **rendered
nowhere**. Handed to the chunk that first renders it, which must distinguish
"not counted" from "counted zero" rather than printing a 0.

### F5 — the Issues list painted every confidence weak · **fixed (S1)**

`issue-row.tsx` and `issue-group.tsx` both rendered `CONFIDENCE_LABEL[...]` in
`var(--confidence-weak)` unconditionally, so the word read **Confirmed** while
the colour said *weak* — a token painting the opposite of its own role, which is
registry rule 13.

The first pass handed this over as a design question. **The answer is no**: the
row already writes the word, so hue would double-encode a value the reader can
already read, and strength-as-colour on a list row is the contradiction rule 13
describes.

**Fix:** both cells render in `var(--text-muted)`, the token the scope and effort
cells beside them already use, keeping one primary cell (the diagnosis) and the
rest secondary. The strength tokens stay where there is no word to read them
from — `bits.tsx` continues to use both.

**Test:** the strength tokens must not appear in either list component, and must
still appear in `bits.tsx`, so the fix cannot be over-applied into a deletion of
the axis.

**Contrast, measured rather than eyeballed.** The rule-13 shape is a token tuned
for one role failing in another, so the replacement was checked at the size and
on the grounds it actually renders at — 12.5px, on `--surface-card` (a top-level
row) and `--surface-page` (a nested one):

| | `--surface-card` | `--surface-page` | worst of all four surfaces |
|---|---|---|---|
| light | 5.79:1 | 5.41:1 | 5.04:1 (`--surface-raised`) |
| dark | 11.71:1 | 12.82:1 | 8.97:1 (`--surface-input`) |

All clear 4.5:1. Two things worth recording:

- **The pixels do not move.** `--text-muted` and `--confidence-weak` resolve to
  the same hex in both themes (`#5e6673` light, `#cdd0d6` dark). The fix changes
  which token is *named*, not what is painted — so it carries no visual risk, and
  the contrast answer is the same before and after. What was wrong was a token
  saying "weak" under the word "Confirmed", and that is fixed regardless of the
  value behind it.
- **No new test was added for this.** `--text-muted` is already discovered as an
  ink token and already asserted against all four surfaces in both themes; the
  contrast test names it explicitly as load-bearing. A second assertion of the
  same fact would be a fresh instance of rule 20.

### F7 — two constants named `EFFORT_ORDER`, meaning different things · **fixed**

`issue-case.ts` had `EFFORT_ORDER` as an array ranking bands for *merging*
(`unknown` loses to any known band). `store.tsx` has `EFFORT_ORDER` as a
`Record<Effort, number>` ranking bands for *sorting* (`unknown` sorts **last**,
value 3). Same name, same concept, same type shape after this pass — opposite
placement of `unknown`. Unifying them would silently break one of the two.

The merge-side constant is now `EFFORT_MERGE_RANK: Record<Effort, number>`,
exhaustive by type, with a comment saying explicitly that it must not be unified
with the other one.

> **On the rename.** Raised as a possible breach of the no-rename rule and ruled
> in scope: that rule targets cosmetic renames, and two constants sharing one
> name with opposite semantics *is* a contradiction. `EFFORT_WIDTH` was the first
> attempt; `EFFORT_MERGE_RANK` says what it does and is what shipped.

### F8 — the ink-token discovery silently drops undefined tokens · **accepted, with a reason**

`discoverInkTokens` ends `.filter((t) => !INK_EXEMPT.has(t) && t in LIGHT)`. A
mistyped token name is not in `LIGHT`, so it is dropped from contrast coverage
rather than reported — a token that renders with no colour at all would be
invisible to the test whose entire purpose is catching that.

Checked: **zero tokens are currently dropped by that filter.** The
locally-scoped pass-throughs the comment mentions (`--segment-tone`) are not
matched by the `color:` pattern in the first place, so the filter is dormant.

Accepted rather than fixed: turning it into an assertion is a real improvement
but not a contradiction, and this pass has no evidence of a live typo. Recorded
so the next pass has a reason to revisit it.

`pages/[id]/page.tsx` carried a type comment justifying itself by "when

### F10 — registry rule 8 was stated in prose and copied into constants · **fixed**

The row the first pass missed. Rule 8 decides the chip scale — "A status chip is
12px, weight 600, and never smaller than 12px. Nothing carrying meaning renders
below 12px — the earlier 11px floor contradicted F3 and is withdrawn." The
figures were then written out again in `status-chip.tsx` as `DEFAULT_FONT_SIZE`,
`MIN_FONT_SIZE` and a literal `fontWeight`, and nothing read the rule. The
withdrawn 11px floor could have come back one component at a time.

**Fix:** the figures are parsed out of the rule text itself and asserted against
what `StatusChip` actually renders — the component is a plain function, so the
test calls it and reads the style off the returned element rather than reading
its source. The clamp is asserted too, since "never smaller than" is the half a
default alone does not deliver, including against a `style` prop trying to push
under it.

The rule's second sentence is about the whole app, so a second test scans every
`.tsx` under `src/components` and `src/app` for a `fontSize` below the floor,
exempting only elements that carry no meaning to lose (`aria-hidden`, or painted
`transparent`).

**It found one live violation:** the Issues list column headers rendered at
11.5px. "State", "Diagnosis", "Scope", "Confidence", "Impact", "Effort" are what
tell you which column you are reading, so they carry meaning. Now 12px. The only
sub-floor size left in the app is a transparent `aria-hidden` spacer in
`ScoreCard.tsx`, which carries none.

## 05 · Registry changes — **installed, v8**

### Rules 20 and 21, new

Both come from the shape of the failures above, not from any one of them.
Accepted verbatim and installed.

**Rule 20 — a fact stated twice is a defect waiting, so state it once.**
Where a second statement is genuinely unavoidable (a pre-paint script that
cannot import; a type that must not reach a provider module), the second copy
carries a test that *executes* or *type-checks* the two against each other. A
comment asking the next editor to remember is not a mechanism. Every failure in
§04 that had a "keep these in step" comment had a comment and nothing else.

**Rule 21 — a test asserts the decision, not the code.**
`expect(migrated.state).toBe("resolved")` passes whatever the registry says.
`expect(migrated.state).toBe(taskStatusWorkState("done"))` fails the moment the
two halves of the decision disagree. Where a test names a literal that
`vocabulary.json` also names, it is asserting a mirror against a mirror and
proves only that two copies agree — never that either is right.

### Rule 18, amended

F3 was a rule 18 violation that rule 18 did not quite cover: it said an absent
measurement is never treated as a value, but not what to do *instead*, and the
two ways of having no reading want opposite answers. The first attempt at the
fix got that wrong in one direction (accepting a fabricated score), the ruling
got it wrong in the other (throwing on ordinary data). Neither reader should
have had to derive it, so rule 18 now says it:

> Absence and malformation are different events and get different answers. A
> reading that was never taken **withholds** the claim that needed it: a claim
> about a group is withheld when any member is unmeasured, while every reading
> that *was* taken still reports — withholding good news must not swallow bad. A
> structure that should carry a reading and does not is a broken invariant, and
> **fails loudly** naming what was malformed. Substituting a value for either —
> a flat delta, a perfect score — is how a claim gets printed over data that
> does not exist.

The version is **v8**, not a second v7: v7 was already committed, and a registry
that changes its content without changing its number is the drift it exists to
prevent.
